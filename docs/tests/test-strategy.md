# テスト戦略 - YouTube市場調査システム (yt-mkt)

## 概要

このドキュメントはPhase 1 (MVP) におけるREDテスト設計戦略を定義します。TDDのREDフェーズとして、**実装前に失敗するテストを設計**し、テストを実行可能な仕様書として機能させます。

## テスト駆動開発 (TDD) の原則

```
RED → GREEN → REFACTOR

RED (このフェーズ):
  - 実装前にテストを書く
  - テストは必ず失敗する (機能が存在しないため)
  - テスト名が仕様を明確に表現する
  - テストが実装のゴールラインになる

GREEN (次フェーズ):
  - REDテストを通す最小限の実装を書く
  - まず動くことを優先、美しさは後回し

REFACTOR (最終フェーズ):
  - テストが通る状態を維持しつつリファクタリング
  - コード品質を高める
```

## テスト技術スタック

```yaml
単体テスト + 結合テスト:
  - Vitest: テストランナー・アサーション
  - React Testing Library: UIコンポーネントテスト
  - MSW (Mock Service Worker): API モック

E2Eテスト:
  - Playwright: ブラウザ自動化

静的解析:
  - TypeScript: 型チェック
  - Biome: リント・フォーマット
```

## テストピラミッド戦略

```
        /\
       /E2E\      (10%) クリティカルユーザージャーニー
      /------\
     / 結合   \    (20%) コンポーネント間・API連携
    /----------\
   /   単体     \  (70%) 関数・ロジック・バリデーション
  /--------------\
```

### 配分の理由

**単体テスト (70%)**
- 最速のフィードバックサイクル
- 関数レベルのロジック検証
- バリデーション、変換、計算ロジック
- API レスポンス処理
- ユーティリティ関数

**結合テスト (20%)**
- コンポーネント + API連携
- フォームの送信フロー
- 状態管理と画面更新の連動
- 認証フロー (OAuth除く)

**E2Eテスト (10%)**
- Google OAuth 認証フロー (実際のOAuthは不可能なのでモック)
- チャンネル検索 → 詳細表示 → スプレッドシート保存
- ダッシュボードの初回ロード → データ表示
- クリティカルパスのみ

## Outside-In TDD戦略

テスト設計の順序: **外側 (ユーザー視点) → 内側 (実装詳細)**

```yaml
1. E2Eレベル (ユーザージャーニー):
   - "ログインしてチャンネル検索してスプレッドシートに保存する"
   - ユーザーが見る・触る振る舞いを定義

2. 結合レベル (コンポーネント連携):
   - "SearchForm が submit されると onSearch が発火する"
   - "API成功時にChannelCardにデータが表示される"
   - コンポーネント間のインターフェースを定義

3. 単体レベル (関数・ロジック):
   - "validateChannelId() が無効なIDでfalseを返す"
   - "formatSubscriberCount() が1234を'1.2K'に変換する"
   - 最も内側のロジックを定義
```

## Phase 1 (MVP) のテスト範囲

### 1. Google OAuth 認証

```yaml
E2Eテスト:

結合テスト:
  - NextAuth.js の Google プロバイダー設定
  - セッション取得・検証
  - 保護されたページへのアクセス制御

単体テスト:
  - セッション状態の判定ロジック
  - トークンの有効期限チェック
```

### 2. Google Sheets 連携

```yaml
E2Eテスト:
  - 初回ログイン時にスプレッドシート自動作成
  - チャンネルデータ保存 → Sheetsに反映確認

結合テスト:

  - 行データのフォーマット変換 (JSON → 2D配列)
```

### 3. YouTube API 連携

```yaml
E2Eテスト:
  - チャンネル検索 → 結果表示 → 詳細取得 → 保存

結合テスト:
  - search.list API呼び出し
  - channels.list API呼び出し (複数ID一括取得)
  - エラーハンドリング (API制限、無効なID、ネットワークエラー)

単体テスト:
  - チャンネルID抽出ロジック
  - APIレスポンスの正規化
  - クォータ計算ロジック
  - キャッシュキーの生成
  - レート制限のチェック
```

### 4. 基本UI (ダッシュボード、検索フォーム)

```yaml
E2Eテスト:
  - ダッシュボード表示 → ナビゲーション → 各ページ遷移
  - 検索フォーム入力 → 検索実行 → 結果表示

結合テスト:
  - SearchForm コンポーネント (入力 → バリデーション → submit)
  - ChannelCard コンポーネント (データ表示 → アクション)
  - Dashboard レイアウト (ナビゲーション + メインコンテンツ)

単体テスト:
  - フォームバリデーション (必須チェック、形式チェック)
  - データフォーマット関数 (数値→K/M表記、日付フォーマット)
  - UI状態管理 (loading, error, success)
  - フィルタリング・ソートロジック
```

## テストの優先度

### P0 (最優先 - クリティカルパス)

```yaml
認証:
  - Google OAuthログイン成功フロー
  - セッション保持
  - 未認証時のリダイレクト

API連携:
  - YouTube チャンネル検索 (正常系)
  - チャンネル詳細取得 (正常系)
  - Google Sheets データ書き込み (正常系)

UI:
  - 検索フォーム送信
  - チャンネル検索結果表示
  - スプレッドシート保存ボタン
```

### P1 (重要 - エラーハンドリング)

```yaml
API連携:
  - API制限エラー (429)
  - 無効なチャンネルID (404)
  - ネットワークエラー
  - タイムアウト

UI:
  - エラーメッセージ表示
  - ローディング状態
  - 空状態 (検索結果0件)
```

### P2 (あれば良い - エッジケース)

```yaml
認証:
  - OAuth失敗時のリトライ
  - トークンリフレッシュ

API連携:
  - キャッシュヒット/ミス
  - バッチ処理の部分失敗

UI:
  - 長いテキストの省略表示
  - 大量データのページネーション
  - レスポンシブデザイン
```

## テストケース設計技法

### 境界値分析

```yaml
チャンネルID:
  - 最小長: 1文字 (無効)
  - 正常: 24文字 (YouTube標準)
  - 最大長: 100文字 (無効)

登録者数:
  - 0 (新規チャンネル)
  - 1,000 (K表記の境界)
  - 1,000,000 (M表記の境界)
  - 10,000,000 (10M+)
```

### 等価分割

```yaml
検索キーワード:
  - 日本語
  - 英語
  - 数字のみ
  - 特殊文字含む
  - 空文字 (無効)
  - 100文字超 (無効)
```

### 状態遷移

```yaml
認証状態:
  未認証 → ログイン中 → 認証済み → ログアウト → 未認証

データ取得状態:
  idle → loading → success → idle
  idle → loading → error → idle
```

## テストデータ戦略

### モックデータの原則

```yaml
1. リアリスティック:
   - 実際のYouTube API レスポンス形式に準拠
   - 実在しそうなチャンネル名・数値

2. 最小限:
   - テストに必要なフィールドのみ
   - 不要な詳細は省略

3. 再利用可能:
   - ファクトリ関数で生成
   - デフォルト値 + 部分オーバーライド

4. エッジケースを網羅:
   - null, undefined, 空文字
   - 最小値、最大値
   - 特殊文字、Unicode、絵文字
```

### MSW (Mock Service Worker) 利用

```yaml
APIモック:
  GET /api/youtube/search:
    - 正常レスポンス (複数チャンネル)
    - 空レスポンス (0件)
    - エラーレスポンス (429, 500)

  GET /api/youtube/channels/[id]:
    - 正常レスポンス (詳細データ)
    - 404 (存在しないID)
    - タイムアウト

  POST /api/sheets/append:
    - 成功
    - 権限エラー
    - ネットワークエラー
```

## REDテストの書き方ガイドライン

### テスト名の命名規則

```typescript
// 悪い例
it('test login')
it('check API')
it('form validation')

// 良い例
it('should redirect to dashboard after successful Google OAuth login')
it('should return 429 error when YouTube API quota is exceeded')
it('should display error message when channel ID is invalid')
it('should format subscriber count 1234567 as "1.2M"')
```

### テスト構造 (Arrange-Act-Assert)

```typescript
describe('ChannelSearch', () => {
  describe('search', () => {
    it('should return channel list when keyword is valid', () => {
      // Arrange: テストデータ・モックの準備
      // Act: 実際の操作・関数呼び出し
      // Assert: 期待結果の検証
    });
  });
});
```

### 一つのテストは一つの振る舞い

```typescript
// 悪い例: 複数の振る舞いを一つのテストで検証
it('should handle login flow', () => {
  // ログイン成功
  // セッション保存
  // ダッシュボード遷移
  // ナビゲーション表示
});

// 良い例: 振る舞いごとに分割
it('should create session when login succeeds')
it('should redirect to dashboard after login')
it('should display user name in navigation after login')
```

## REDテスト設計フロー

```yaml
Step 1: 機能を振る舞いに分解
  入力: "チャンネル検索機能"
  分解:
    - キーワードでチャンネルを検索できる
    - 検索結果が一覧表示される
    - 無効なキーワードでエラーが返る
    - API制限時に適切なエラーメッセージが表示される
    - 検索結果をクリックすると詳細が表示される

Step 2: 優先度付け (P0 → P1 → P2)
  P0: 正常系 (キーワード検索成功、結果表示)
  P1: 異常系 (無効なキーワード、APIエラー)
  P2: エッジケース (空結果、大量結果)

Step 3: REDテスト仕様を書く
  - テストケース名
  - 前提条件 (Arrange)
  - 操作 (Act)
  - 期待結果 (Assert)
  - ※ 実装コードは書かない

Step 4: team-test-exec に引き渡し
  - REDテスト仕様ドキュメント
  - 優先順序
  - 各テストの意図・背景
```

## 次のステップ

1. `red-tests-auth.md`: 認証フローのREDテスト仕様
2. `red-tests-api.md`: API連携のREDテスト仕様
3. `red-tests-ui.md`: UIコンポーネントのREDテスト仕様

各ドキュメントには以下を記載:
- テストケース一覧 (優先度付き)
- 各テストの詳細仕様 (Arrange-Act-Assert)
- モックデータの定義
- 期待される振る舞いの明確な記述

## 成功基準

REDテストが成功したと言える条件:

1. 全てのREDテストが実行できる (構文エラーなし)
2. 全てのREDテストが失敗する (実装が存在しないため)
3. テスト名を読むだけで仕様が理解できる
4. テストが通れば機能が完成したと判断できる
5. 実装の詳細に依存していない (インターフェースのみテスト)
