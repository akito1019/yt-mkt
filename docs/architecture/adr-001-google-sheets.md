# ADR-001: Google Sheetsをデータストアとして採用

## ステータス

**承認** (2026-03-03)

## コンテキスト

YouTube市場調査システム (yt-mkt) では、以下のデータを永続化する必要がある:

1. **チャンネル情報**: YouTube Data APIから取得したチャンネルのメタデータ
2. **履歴データ**: チャンネルの登録者数・再生数の日次推移
3. **動画情報**: チャンネル別の動画リスト
4. **ジャンル定義**: ユーザーが定義したジャンル分類
5. **分析結果キャッシュ**: 参入難易度スコア等の計算結果

### 要件

**機能要件**:
- データの永続化（読み取り・書き込み・更新・削除）
- 時系列データの蓄積（日次の成長率計算のため）
- ユーザーごとの独立したデータ空間
- データのエクスポート機能（分析結果の共有）

**非機能要件**:
- 初期開発コスト: 低い（MVP開発期間: 2週間以内）
- 運用コスト: 無料または低額（月額$5以下）
- スケーラビリティ: ユーザー数100人、チャンネル数10,000件程度
- 可用性: 99%以上（Google Cloud SLA）
- データポータビリティ: ユーザーが自由にデータにアクセス可能

**制約**:
- Google OAuth 2.0 を使用した認証（技術スタック決定済み）
- Vercel へのデプロイ（サーバーレス環境）
- 開発者は個人（フルマネージドサービスが望ましい）

## 決定

**Google Sheets API v4** をプライマリデータストアとして採用する。

### 採用理由

1. **ユーザー体験の最大化**
   - Googleアカウントでログイン → 自動的にGoogleドライブにスプレッドシートが作成される
   - ユーザーは自分のスプレッドシートを直接閲覧・編集・バックアップ可能
   - データのエクスポート機能が不要（すでにスプレッドシート形式で存在）
   - 他のユーザーへの共有が容易（Googleドライブの共有機能）

2. **開発効率**
   - Google Sheets API v4 は REST API として利用可能（学習コスト低）
   - NextAuth.js との統合が容易（Google OAuth Provider）
   - スキーマ設計が柔軟（シート・列の追加が容易）
   - ローカル開発環境でのセットアップが簡単（APIキーのみ）

3. **コスト最適化**
   - Google Sheets API: 無料枠 500 requests/100秒（十分）
   - ストレージ: Googleドライブ無料枠 15GB（スプレッドシートは容量消費少）
   - インフラコスト: ゼロ（データベースサーバー不要）
   - バックアップコスト: ゼロ（Google自動バックアップ）

4. **運用の簡素化**
   - データベースのメンテナンス不要（マイグレーション、バックアップ、監視）
   - スケーリングの考慮不要（Googleインフラに依存）
   - 障害対応不要（Google Cloud SLA 99.9%）

5. **データポータビリティ**
   - ベンダーロックインのリスク低減（スプレッドシート形式は標準的）
   - データ移行が容易（CSV/Excel エクスポート可能）
   - 将来的に別のDBへ移行する場合でも、データ抽出が容易

## 検討した代替案

### 代替案1: PostgreSQL (Supabase/Neon)

**メリット**:
- リレーショナルデータベースの利点（ACID特性、トランザクション、JOIN）
- SQL による強力なクエリ機能
- スキーマによる厳密なデータ検証
- パフォーマンス（インデックス、最適化されたクエリ）

**デメリット**:
- セットアップコスト（マイグレーション、ORM設定）
- 運用コスト（有料プラン: $25/月〜）
- ユーザーがデータに直接アクセス不可（専用のエクスポート機能が必要）
- バックアップ・リストア戦略の設計が必要
- ローカル開発環境の複雑化（Docker等）

**不採用の理由**:
- MVP段階では、リレーショナルDBの複雑な機能は不要
- データポータビリティの要件を満たさない
- 運用コストが要件（$5以下）を超える

### 代替案2: MongoDB Atlas

**メリット**:
- スキーマレス設計（柔軟なデータ構造）
- JSON形式で直感的
- スケーラビリティ（シャーディング）
- フルマネージド（バックアップ自動）

**デメリット**:
- 無料枠の制約（512MB、将来的に不足の可能性）
- ユーザーがデータに直接アクセス不可
- クエリ言語の学習コスト（MongoDB Query Language）
- 時系列データの扱いがRDBMSより弱い

**不採用の理由**:
- データポータビリティの要件を満たさない
- 時系列データ（履歴テーブル）の分析がやや複雑
- ユーザーがスプレッドシートで直接閲覧できる利点が失われる

### 代替案3: Firebase Firestore

**メリット**:
- Google エコシステムとの統合
- リアルタイムデータベース機能
- オフラインサポート
- 自動スケーリング

**デメリット**:
- NoSQLのため、複雑なクエリが困難
- コスト（読み取り・書き込みごとに課金、予測困難）
- ユーザーがデータに直接アクセス不可
- データ構造の変更が複雑（ドキュメント・コレクション設計）

**不採用の理由**:
- リアルタイム機能は要件にない（オーバースペック）
- 従量課金モデルがコスト予測を困難にする
- データポータビリティの要件を満たさない

### 代替案4: ローカルストレージ (IndexedDB)

**メリット**:
- サーバーサイドストレージ不要
- 完全無料
- 高速なデータアクセス

**デメリット**:
- デバイス間でのデータ同期が不可
- データバックアップが困難
- ストレージ容量の制約（ブラウザ依存）
- データの永続性が保証されない（ユーザーがキャッシュクリア可能）

**不採用の理由**:
- データの永続化要件を満たさない
- 複数デバイスからのアクセス不可
- 時系列データの蓄積に不向き

## 決定の影響

### ポジティブな影響

1. **開発速度の向上**
   - データベース設計・マイグレーション不要 → MVP開発期間短縮
   - 認証とデータストアが同一のGoogleアカウント → 統合が容易
   - スキーマ変更が容易 → 段階的な機能追加に対応

2. **ユーザー価値の向上**
   - データの完全な透明性（スプレッドシートで確認可能）
   - データの自由な編集・分析（Googleスプレッドシートの関数・グラフ機能）
   - データのポータビリティ（他ツールへのインポート容易）

3. **運用コストの削減**
   - インフラコスト: $0
   - メンテナンスコスト: ほぼゼロ
   - バックアップコスト: $0

4. **スケーラビリティ**
   - 初期段階（100ユーザー）では全く問題なし
   - Google Sheetsの制限（500万セル/スプレッドシート）で、1ユーザーあたり10,000チャンネル程度は保存可能

### ネガティブな影響とリスク軽減策

#### リスク1: パフォーマンスの限界

**問題**:
- Google Sheets API のレートリミット（500 requests/100秒）
- スプレッドシートの行数制限（500万セル）
- クエリ速度（RDBMSと比較して遅い）

**軽減策**:
- **バッチ処理**: 複数行の読み書きを1回のAPIコールで実行（batchUpdate, batchGet）
- **キャッシュ戦略**: Next.js ISRとブラウザキャッシュで読み取り回数削減
- **アーキタイプパターン**: 将来的にPostgreSQLへ移行可能な抽象化層を設計
  ```typescript
  // Repository Pattern で抽象化
  interface ChannelRepository {
    findById(id: string): Promise<Channel>
    save(channel: Channel): Promise<void>
  }

  class SheetsChannelRepository implements ChannelRepository { ... }
  // 将来: class PostgresChannelRepository implements ChannelRepository { ... }
  ```

#### リスク2: トランザクションの欠如

**問題**:
- Google Sheets にはトランザクション機能がない
- 複数シートの更新中にエラーが発生すると、データ不整合のリスク

**軽減策**:
- **Idempotency（冪等性）**: APIエンドポイントを冪等に設計（同じリクエストを複数回実行しても安全）
- **楽観的ロック**: 更新時に version カラムをチェック
- **補償トランザクション**: エラー時のロールバック処理を実装
- **データ検証**: 読み取り時にデータ整合性を検証し、不整合があれば修復

#### リスク3: 複雑なクエリの制限

**問題**:
- SQLのようなJOIN、GROUP BY、サブクエリが使えない
- 複雑な分析クエリはアプリケーション側で処理が必要

**軽減策**:
- **アプリケーション層での集計**: 参入難易度スコア等の複雑な計算はNode.js側で実装
- **分析結果のキャッシュ**: 計算結果を `analysis_cache` シートに保存
- **必要に応じたデータベース追加**: Phase 4（高度な分析）で、分析専用にPostgres/BigQueryを追加検討
  - Google Sheets: マスターデータ（ユーザーが直接編集可能）
  - Postgres: 分析用データウェアハウス（読み取り専用）

#### リスク4: スケーラビリティの天井

**問題**:
- 1ユーザーが10,000チャンネル以上を保存する場合、スプレッドシートの限界に達する

**軽減策**:
- **データアーカイブ戦略**: 古いデータを別スプレッドシートに移動
- **段階的移行計画**: ユーザー数が1,000人を超えた時点で、PostgreSQLへの移行を検討
- **移行の容易性**: Repository Pattern により、移行時のコード変更を最小化

#### リスク5: セキュリティ

**問題**:
- ユーザーがスプレッドシートを誤って削除するリスク
- スプレッドシートを他人に共有した場合のデータ漏洩リスク

**軽減策**:
- **アクセス制御**: OAuth スコープを `drive.file` に限定（アプリが作成したファイルのみアクセス）
- **削除検出**: スプレッドシートが削除された場合、アプリ側で検出し再作成を提案
- **ユーザー教育**: 初回利用時に、スプレッドシートの扱い方を説明

## 移行計画（将来）

### トリガー条件

以下のいずれかの条件を満たした場合、PostgreSQLへの移行を検討:

1. **パフォーマンス**: API レートリミット到達（500 req/100秒）が頻発
2. **スケール**: ユーザー数 1,000人 または チャンネル総数 100,000件 突破
3. **機能要件**: 複雑なクエリ（JOIN、全文検索）が必要な機能の追加
4. **ユーザー要望**: データポータビリティよりもパフォーマンスを優先する声が多数

### 移行戦略

```
Phase A: 並行運用期間（3ヶ月）
  - PostgreSQL を追加（Google Sheets と併用）
  - 新規データはPostgreSQLに保存、Google Sheetsにも同期
  - 読み取りはPostgreSQLを優先、フォールバックでGoogle Sheets

Phase B: 段階的移行期間（3ヶ月）
  - 既存ユーザーデータをPostgreSQLへ移行（バッチ処理）
  - ユーザーには「データ移行完了」通知
  - Google Sheetsはエクスポート機能として残す

Phase C: 完全移行（1ヶ月）
  - Google Sheetsへの書き込みを停止
  - 読み取りはPostgreSQLのみ
  - エクスポート機能でCSV/Excel生成
```

### 移行コスト見積もり

```
開発コスト:
  - Repository 実装: 2週間
  - データ移行スクリプト: 1週間
  - テスト・QA: 1週間
  合計: 4週間（1人月）

運用コスト:
  - Supabase Pro: $25/月
  - または Neon Scale: $19/月

並行運用コスト:
  - Google Sheets API: $0（無料枠内）
  - Postgres: $19-25/月
  合計: $19-25/月（Phase C完了後）
```
